# Login con JWT (API + interfaz)

- **Fecha:** 2026-09-25
- **Tipo:** trabajo
- **Archivos / tablas involucrados:** `api/` (composer.json, config, libraries, core, controllers, models), `interfaz/` (services, stores, router, Login, Navbar, Dashboard, vite.config.js), tablas `usuario`, `rol`, `empresa` (solo lectura)

## Objetivo

Conectar el login de la interfaz con la BD a través de la API, usando JWT.

## Qué se hizo

**Análisis previo** (presentado y aprobado antes de programar):
- `usuario`: 5 usuarios activos, 1 empresa. `clave` ya en bcrypt (`$2y$`, 60 caracteres) → `password_verify()` sin cambios en la BD. `alias` sin índice único, sin repetidos hoy. No hay tablas de tokens ni de sesiones.
- `General_model` lee `$this->session->userdata()` en el constructor y se carga en `autoload.php`, pero la sesión no se cargaba: cualquier petición a la API habría fallado.
- En este equipo, `localhost` en Apache apunta a otro proyecto (un VirtualHost con `DocumentRoot` distinto), así que `http://localhost/logy/api/` da 404. No se tocó Apache; en desarrollo la API corre con `php -S`.

Consultas (solo lectura, sesión `READ ONLY`, sin imprimir datos personales):

```sql
SELECT COUNT(*) total, SUM(activo) activos, COUNT(DISTINCT empresa_id) empresas FROM usuario;
SELECT LEFT(clave,4) prefijo, LENGTH(clave) largo, COUNT(*) n FROM usuario GROUP BY prefijo, largo;
SELECT (SELECT COUNT(*) FROM (SELECT alias FROM usuario GROUP BY alias HAVING COUNT(*)>1) a) global_dup,
       (SELECT COUNT(*) FROM (SELECT alias FROM usuario GROUP BY alias, empresa_id HAVING COUNT(*)>1) b) empresa_dup;
SHOW INDEX FROM usuario;
SELECT id, empresa_id, rol_id FROM usuario WHERE activo = 1 ORDER BY id LIMIT 1;  -- para las pruebas de token
```

**Decisiones del usuario**: sesión sin estado con `Sesion_token`; formato `{ exito, datos, mensaje }`; token de 8 h; login solo con alias; axios en la interfaz; firebase/php-jwt en la versión compatible con PHP 7.4. Ver `decisions/0004-autenticacion-jwt.md`.

**API**:
- `api/composer.json` del proyecto con `firebase/php-jwt ~6.10.0` (instalada la 6.10.0), `vendor` en `application/vendor`, y el aviso `PKSA-y2cr-5h3j-g3ys` ignorado de forma explícita. `config.php`: `composer_autoload` apunta a ese vendor.
- `config/jwt.php`: clave de 64 bytes aleatorios (generada sin mostrarse), emisor `logy-api`, duración 8 h.
- `libraries/Token_jwt.php` (genera y valida; clave mínima de 32 bytes, HS256 fijo, exige `exp` e `iss`) y `libraries/Sesion_token.php` (lee el Bearer token y se registra como `session`).
- `autoload.php`: `database` y `'sesion_token' => 'session'`.
- `core/MY_Controller.php`: `MY_Controller` (`responder`, `responderError`, `entrada`, `exigirMetodo`) y `Autenticado_Controller` (401 sin token válido). *(Reemplazado ese mismo día por el helper `api_helper.php`; ver `2026-09-25-helper-api.md`.)*
- `controllers/Auth.php`: `POST auth/login` y `GET auth/yo`.
- Modelos `Usuario_model`, `Rol_model`, `Empresa_model` (extienden `General_model`, regla 5). `Usuario_model::autenticar()` verifica siempre contra un hash ficticio cuando el alias no existe, para no delatar qué usuarios existen por el tiempo de respuesta.

**Interfaz**:
- `axios` instalado. `services/api.js`: instancia con `baseURL` `/api`, agrega el token y cierra la sesión ante un 401 (salvo en `auth/login`). `mensajeError()` convierte errores en texto.
- `stores/sesion.js`: token, usuario y vencimiento. "Recordarme" → `localStorage`; si no, `sessionStorage`.
- `router/index.js`: `meta.publica` y guardia `beforeEach` (sin sesión → `/login?redirect=…`; con sesión, `/login` → `/`). El `redirect` solo acepta rutas internas.
- `Login.vue` llama a la API y muestra sus errores; campo "Usuario" (alias). `Navbar.vue` y `Dashboard.vue` usan el usuario de la sesión; se quitó `usuarioDemo` de `config/app.js`.
- `vite.config.js`: proxy `/api` → `http://localhost:8080/index.php`. Script `npm run api` (levanta `php -S localhost:8080 -t ../api`). `.claude/launch.json` con la configuración `api`.

## Hallazgos / resultado

Pruebas (API con `php -S`, interfaz en una segunda instancia de Vite en el puerto 5174):
- `auth/login`: vacío → 422; alias inexistente → 401 "Usuario o contraseña incorrectos."; GET → 405.
- `auth/yo`: sin token → 401; token válido → 200 con `id, nombre, alias, correo, telefono, foto, rol, empresa` (nunca `clave`); vencido, firmado con otra clave, `alg: none` y otro emisor → 401. Un token generado con `JWT::encode` también se acepta.
- Navegador: sin sesión, `/usuarios` → `/login?redirect=/usuarios`; credenciales incorrectas muestran el error de la API; con un token de prueba (5 minutos) se entra, el navbar muestra el perfil real y "Cerrar sesión" borra el token y vuelve al login; un token inválido guardado lleva al login y se borra.
- **No se probó un login real con contraseña correcta**, porque Claude no conoce ninguna. Lo debe probar el usuario.
- El servidor de Vite que ya estaba corriendo no tomó el proxy nuevo: hay que reiniciarlo. En la primera prueba del usuario, `POST /api/auth/login` recibió un 404 vacío de Vite (la petición nunca llegó a la API) y la interfaz mostró "Ocurrió un error inesperado". Se ajustó `mensajeError()` para que una respuesta que no viene de la API muestre "No se pudo conectar con la API. Verifica que esté en ejecución."
